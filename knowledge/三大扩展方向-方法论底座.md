# 三大扩展方向方法论底座

> 用途：为「医信顾问」与「医疗信息化交付团」补充三个国内强需求方向的方法论。
> 各 agent 的能力条目引用本文档，但 agent 自身必须自包含关键判断规则，不得假设能读到本文件。
> 所有政策文号、标准编号、指标数值均为公开常识性表述，未核实的具体条款一律标注「待核」并挂责任方。

---

## 方向一：可信数据空间（Trusted Data Space）

### 1.1 它是什么，不是什么

- **是**：一种数据流通利用基础设施，让数据「**不出域、可用不可见**」，在跨机构协作中实现「原始数据不动、价值流动」。国家数据局 2024 年印发《可信数据空间发展行动计划（2024—2028 年）》，把企业、行业、城市、跨境四类可信数据空间列为重点。
- **不是**：不是又一个数据中台，不是数据库产品，也不是单纯的隐私计算平台。中台解决「自己看得见」，可信数据空间解决「别人用得上但拿不走」。
- **医疗定位**：属「行业可信数据空间」，面向跨院、医共体、医教研、医保-医疗协同的数据协作。

### 1.2 核心能力栈（判断一个方案是否可信数据空间的五要素）

| 要素 | 判断问题 | 常见落法 |
|---|---|---|
| 数据可控 | 数据离开原域后，提供方是否仍掌握使用权与收回权？ | 使用控制（Usage Control）、数字合约、数据指纹 |
| 隐私计算 | 跨方计算时能否做到「数据可用不可见」？ | 联邦学习、多方安全计算（MPC）、可信执行环境（TEE） |
| 身份可信 | 参与方、设备、应用是否可验证且可追溯？ | 可信身份认证、接入准入、CA 证书 |
| 全程审计 | 数据被谁、何时、用于何事是否可举证？ | 全链路日志、存证（区块链/留痕）、可追溯 |
| 价值分配 | 数据贡献能否计量、定价、结算？ | 数据资产登记、贡献度计量、收益分配机制 |

### 1.3 医疗场景落地路径

1. **选场**：优先选「多方都有意愿、单方拿不全数据」的场景——多中心科研、专病队列、区域慢病管理、医保基金协同监管。避免一上来做「全院数据入空间」。
2. **定契约**：先明确数据权属、使用范围、留存期限、退出机制，再谈技术。契约不清是项目失败的第一原因，不是技术不达标。
3. **搭底座**：身份可信 + 使用控制先上，隐私计算按需选（联邦学习适合模型训练，MPC 适合联合统计，TEE 适合高性能计算）。
4. **跑通单点**：用一个具体课题验证「数据不出域」闭环，拿到可举证的结果再扩展。
5. **合规先行**：数据安全法、个人信息保护法、健康医疗数据安全相关国家标准（编号待核）与等保要求同步满足。

### 1.4 常见失败模式（红线）

- 把「建了个数据交换平台」当成可信数据空间——缺使用控制与审计，数据一旦导出即失控。
- 只谈技术不谈契约——数据权属与收益分配没谈拢，参与方不会真授权。
- 隐私计算选型跟风——联邦学习解决不了所有问题，通信成本、参与方在线率、模型收敛都要评估。
- 敏感个人信息未单独同意即入空间——健康医疗数据属敏感个人信息，需单独同意与最小必要。

## 方向二：三医融合（医疗 / 医保 / 医药）

### 2.1 概念边界

- **三医**：医疗（医院与卫健体系）、医保（支付与基金监管）、医药（药品耗材供应与合理使用）。
- **融合目标**：医保支付方式改革（DRG/DIP）、药品耗材集中带量采购、医疗服务价格调整三者联动，数据打通是前提。
- **对医院信息化的影响**：从「以收费为中心」转向「以病案质量、成本管控、合理诊疗为中心」，对病案首页质量、临床路径、成本核算提出硬要求。

### 2.2 三医融合对系统的硬性要求

| 域 | 系统/数据要求 | 常见短板 |
|---|---|---|
| 医疗 | 病案首页质量、临床路径、电子病历分级 | 首页填写质量差，DRG 入组失真 |
| 医保 | DRG/DIP 分组、医保结算清单、智能监控 | 结算清单与病案口径不一致 |
| 医药 | 药品耗材 Spd、合理用药、追溯码 | 集采中选落地的库存与替代管理薄弱 |

### 2.3 DRG/DIP 落地的关键判断

1. **口径一致**：病案首页、医保结算清单、DRG 分组器三者口径必须对齐；口径不同导致的「亏损病组」是假象，先查口径再谈控费。
2. **成本可信**：病种成本要能核算到项目级，做不到就别急着做「病组盈亏分析」——分母不清的盈利率比没有更危险。
3. **行为不变形**：控费不能诱导推诿重症、分解住院。方案里必须写监控指标（如 CMI 值、再入院率）防止变形。
4. **不虚构规则**：分组方案版本、权重、分值、监管条款以当地医保局发文为准，未核实的写「待核」，不得用全国口径套地方。

### 2.4 常见失败模式（红线）

- 把 DRG/DIP 当成纯医保科的事——它倒逼的是全院病案、临床、运营协同，缺医务与病案参与必失败。
- 用「平均数」掩盖结构问题——例均费用下降可能来自病例结构变化，必须看 CMI 校正后指标。
- 集采落地只看采购价——中选后供应保障、临床替代、患者教育没跟上，会出现断供与投诉。

## 方向三：信创可信（国产化替代 + 安全可信）

### 3.1 两个词分开理解

- **信创**（信息技术应用创新）：芯片、操作系统、数据库、中间件、整机的国产化替代。医疗行业常见栈——芯片（鲲鹏/飞腾/海光/兆芯/龙芯，路线待核）、操作系统（麒麟/统信 UOS）、数据库（达梦/人大金仓/openGauss 等）、中间件（东方通/金蝶等）、整机（华为/浪潮等）。具体型号与兼容性以当期信创目录与实测为准。
- **可信**：网络安全等级保护（等保 2.0）、商用密码应用安全性评估（密评）、可信计算、数据分类分级。信创解决「自主可控」，可信解决「安全合规」，两者是两条线，不能互相替代。

### 3.2 医疗信创替换路线（顺序是成败关键）

1. **先外围后核心**：办公、门户、非核心系统先行；HIS/EMR/LIS/PACS 核心系统最后动。
2. **先数据库兼容层**：核心系统替换往往卡在数据库方言与存储过程，先做兼容评估与改造，再换 OS 与芯片。
3. **双轨并行**：新旧环境并行运行一个完整业务周期（含月末、季度结算），比对结果一致再切换。
4. **回退预案**：每个切换点必须有可验证的回退路径与回退判定标准，没有回退方案的切换不得执行。

### 3.3 等保与密评要点

- **等保 2.0**：定级（二级/三级常见）→ 备案 → 建设整改 → 测评 → 监督检查。三级系统测评要求与周期以现行标准为准（条款编号待核）。
- **密评**：商用密码应用安全性评估，关注身份鉴别、数据传输/存储机密性与完整性、不可否认性；使用国密算法（SM2/SM3/SM4）的合规性需实测。
- **数据分类分级**：健康医疗数据按敏感程度分级，敏感个人信息（病历、生物识别、基因）单独保护，入空间、出域、共享均需分级授权。

### 3.4 常见失败模式（红线）

- 把信创当成「换牌子」——只换硬件不验证性能，核心系统上线後卡顿、宕机。必须做性能基线与压力测试。
- 核心系统与外围同时切换——没有双轨比对，出了问题分不清是业务 bug 还是兼容问题。
- 等保/密评「测评时临时补」——合规是设计出来的，不是测评前突击出来的；架构阶段不介入，后期改造成本翻倍。
- 混淆信创与可信——用了国产数据库不等于过了密评，合规结论只能来自对应测评。

## 三方向的交叉点（交付团编排提示）

- 可信数据空间 × 三医融合：医保-医疗数据协同是可信数据空间最典型的医疗落地场，但必须先解决 DRG/结算清单口径一致性，否则「可用不可见」的是错误数据。
- 三医融合 × 信创可信：DRG 分组器、医保结算接口在信创环境下的兼容性是高频坑，架构评审必须单列。
- 可信数据空间 × 信创可信：数据不出域的底座（身份、审计、使用控制）应优先部署在信创环境，避免「数据可信了、底座不可控」。
